# P2P 60-24 OneClick Evo — Project Constitution

**Version:** 0.1 DRAFT
**Status:** CONTROLLED — NOT YET FROZEN
**Purpose:** canonical project-level foundation for human and AI collaboration

> This document is a controlled reconstruction of the project vision and previously established principles. It becomes authoritative only after human approval.

## 1. Identity of the Project

P2P 60-24 OneClick Evo is a privacy-oriented, decentralized computing and agent network intended to operate as a resilient, cooperative digital organism rather than as a conventional centralized platform.

The system is built around autonomous nodes, direct communication, contextual trust, local memory, modular capabilities and controlled evolution.

The core lifecycle is:

`invite → identity → handshake → trust → task → verification → memory → evolution`

## 2. Purpose

The project seeks to give people and their devices a practical, decentralized infrastructure in which useful computation, communication, knowledge and cooperation can emerge without requiring a single central authority.

**OneClick** expresses ease of deployment. **Evo** expresses controlled evolution. **60-24** is the project identity and continuity marker.

## 3. Core Values

1. Human benefit and positive use.
2. Privacy and user control.
3. Decentralization and resilience.
4. Verifiable knowledge over unsupported claims.
5. Trust based on relationships, context and evidence.
6. Minimalism over unnecessary complexity.
7. Emergence over unnecessary central control.
8. Interoperability and open standards where practical.
9. Controlled evolution rather than uncontrolled mutation.
10. Human responsibility for fundamental decisions.

## 4. What the System Is Not

P2P 60-24 is not to become:

- a centralized surveillance platform;
- an advertising-driven platform;
- a financial token or wallet system;
- a payment processor;
- an opaque global reputation score for people;
- a system that treats AI output as unquestionable truth.

## 5. Trust Infrastructure

Trust is infrastructure for cooperation, not a commodity and not a financial instrument.

Trust is intended to be:

- relational;
- contextual;
- directional where appropriate;
- based on evidence and observed interactions;
- capable of decay over time;
- resistant to Sybil and collusion attacks;
- explainable rather than an opaque single global score.

The Trust Infrastructure must remain separated from money, payments and financial incentives unless a future constitutional decision explicitly establishes a compatible boundary.

## 6. Privacy and Locality

The default design preference is local-first operation. Data should remain on the user's node unless sharing is necessary, authorized and governed by the relevant protocol.

Decentralization does not mean indiscriminate data replication.

## 7. Human–AI Relationship

AI agents are engineering partners, analysts and executors within defined autonomy boundaries. They do not own the project's intent.

**System suggests. Human decides.**

AI may discover conflicts, propose alternatives, implement approved work and provide evidence. Constitutional changes require human approval.

## 8. Architecture Principles

The architecture should favour:

- modularity;
- event-driven communication;
- explicit contracts;
- transport abstraction;
- local autonomy;
- verifiable state transitions;
- resilient peer-to-peer communication;
- reproducible builds and tests;
- observability without unnecessary surveillance.

Biological metaphors such as organism, cells, DNA, immune system or nervous system are architectural inspiration, not claims that the software literally reproduces biological processes.

## 9. Evolution Rule

New ideas must pass:

`REUSE → INTEGRATE → IMPROVE → INVENT → REJECT / ESCALATE`

Existing project knowledge must be checked before introducing competing concepts.

Experiments remain isolated until explicitly promoted into architecture.

## 10. Knowledge and Evidence

Project knowledge is separated into:

- Constitution — why and what must remain true;
- Ontology — what exists and how concepts relate;
- Architecture — how the system is constructed;
- ADRs — why significant technical choices were made;
- Code — implementation;
- Tests — executable evidence;
- Sessions — record of process and continuity.

Conversation memory is not the project's source of truth.

## 11. Security Boundary

Security is a foundational property, not a later add-on. Identity, authentication, authorization, sandboxing, anti-Sybil measures, replay protection and secure transport must be designed according to actual threat models and verified by tests.

No agent should execute untrusted generated code without an appropriate isolation boundary.

## 12. Constitutional Protection

The following areas require human decision:

- project purpose and fundamental values;
- foundational ontology;
- Trust Infrastructure principles;
- fundamental privacy and security boundaries;
- governance and AI autonomy boundaries;
- changes to frozen invariants.

A proposal must document motivation, alternatives, impact and evidence.
